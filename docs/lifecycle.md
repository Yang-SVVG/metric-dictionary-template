# 指标生命周期

```text
draft ──评审通过──▶ active ──不推荐使用──▶ deprecated
  ▲                    │                        │
  └────────退回─────────┘                        └──下线（含数据保留期）──▶ 删除记录
```

## draft

- 有人在用、但口径还没对齐（典型：业务口头定了，还没和数据团队确认）；
- 允许出现在分析里，**不允许出现在对外报表**；
- 必须填 owner —— 没有 owner 的 draft 就是「谁的都不算」的孤儿指标。

## active

进入 active 的门槛（缺一不可）：

1. 定义、公式、来源表、粒度、单位、owner 六项齐全；
2. 公式引用的表都在 `sql/` 里声明；
3. 有至少一个下游看板/报表在用（没有消费者的指标不该占坑）；
4. 经过一次复核（`updated_at` 即复核日期）。

## deprecated

- 保留历史数据与定义，禁止新报表引用；
- `definition` 末尾必须写清替代指标，例：`【已废弃，见 gmv_order_paid_v2】`；
- 至少保留 180 天再删，给下游迁移窗口。

## 变更规程

| 变更类型 | 处理方式 |
| --- | --- |
| 改错别字、补注释 | 直接改，`version` 不变 |
| 改过滤条件（口径变了） | `version + 1`，新建一条记录，旧版本转 deprecated |
| 换来源表 | `version + 1` + 血缘表追加一行，必须写迁移说明 |
| 删除 | 只能 deprecated，不能直接消失 |

**口径变更必须留痕**：同一 `metric_code` 出现多个 `version` 是正常的，
「一个 code 一条记录、改了就覆盖」才是事故源头 —— 三个月后没人能解释去年同期数字为什么跳变。

## 复核节奏

- `updated_at` 超过 180 天 → 校验器给 `STALE_METRIC` warning；
- 财务/合规口径建议 90 天，可在 CI 里传 `--max-age-days 90`；
- 复核不是走过场：要么重算一遍对得上，要么把「本次核对无变化」写进变更记录。
