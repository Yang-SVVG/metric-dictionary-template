# 口径治理流程与评审清单

> 目标：让「这个指标到底怎么算」这个问题，在全公司只有一个答案、一个 SQL。

## 一、新增/变更指标的标准流程

```
提出需求 → 草稿(draft) → 评审 → 生效(active) → 定期复核 → 下线(deprecated)
```

1. **提出**：任何团队都可以提，但必须写清「谁用、用来做什么决策」。答不上来的指标不进字典。
2. **草稿**：在字典里填 `definition` / `formula` / `source_tables` / `grain` / `unit` / `owner`，状态 `draft`。
3. **评审**：口径负责人 + 至少一个使用方一起过清单（见下）。评审记录写进 `dim_metric_version.change_note`。
4. **生效**：状态改 `active`，同时写入 `effective_at`；报表口径以生效时间之后为准。
5. **复核**：超过 180 天未复核的指标由校验器提示，负责人确认「口径未变」并更新 `updated_at`。
6. **下线**：业务不再使用的指标标 `deprecated`，保留历史口径供追溯，**不删除**。

## 二、评审清单（每次口径变更必过）

- [ ] **定义能被业务方复述**：一句话说清「算什么、不算什么」，不能出现「大概」「一般」。
- [ ] **排除项明确**：退款、取消、测试单、内部单是否剔除，写死在公式里而不是口头约定。
- [ ] **时间口径明确**：按支付时间、发货时间还是完成时间？跨时区怎么算？
- [ ] **来源表唯一**：公式里出现的表都在 `source_tables` 里，血缘没有暗表。
- [ ] **粒度声明**：日/周/月，以及月是自然月还是滚动 30 天。
- [ ] **单位与精度**：元/万元、%还是千分比、保留几位小数。
- [ ] **负责人**：出了问题找谁，不能是「那个组」。
- [ ] **历史是否需要重算**：口径变更后，历史报表是重跑还是加版本标记？

## 三、常见误区

| 误区 | 后果 | 正确做法 |
| --- | --- | --- |
| 口径写在 Excel 备注里 | 三个月后没人看懂 | 进字典，进版本表 |
| 一个指标三种算法并存 | 开会先对账半小时 | 一个编码一个公式，冲突走评审 |
| 公式里 join 未登记的表 | 源头换了也没人发现 | 血缘校验失败即阻断 |
| 下线直接删记录 | 历史报表无法解释 | 标 `deprecated` 并保留快照 |
| 字典做成一次性文档 | 半年后与现状脱节 | 字典进 CI，变更必须过校验 |

## 四、怎么把这套东西推销出去（治理最难的部分）

- **从痛的地方开始**：先挑一个「每次开会都要对账」的指标，把它的口径做扎实，用一次会议证明有效。
- **降低使用成本**：提供 SQL 片段和视图（`v_active_metric`），让业务方不需要读文档也能取数。
- **让不合规可见**：校验器输出 error/warning，评审会直接看报告，而不是靠人盯。
- **不追求全覆盖**：先覆盖 Top 20 核心指标，剩下的按需补齐；一次治理全量指标的项目通常死在第三周。
